## Decisions in force

- D1 A model decomposes any SPEC; there is no required SPEC format and no embedded block: Option B, decided by the user. mitosis reads whatever document the author already wrote. There is no embedded block, no schema, no required section, no validate command, and no canonical example SPEC - because there is no format to teach. INTENT: the question that opened this whole investigation was "how would any SPEC architect know what the block requires from one line of instruction." Option B deletes the question rather than answering it. A required format needs a specification, a validator, example documents and good error messages, and every one of those exists only to check something a model can emit directly. ACCEPTED COST: two runs on the same SPEC may split the work differently, and nobody hand-designed the split, so it is only as good as the model. WHAT THIS KILLS: the entire phase-1 validation surface of the old design - seventeen rejection rules, the fence grammar, the accepts/example error strings, the value field, the no-task rule, the completeness critic. None of them survive. Do not restore any of them.
- D2 A planning phase per MSP; correctness is planner-designed invariants asserted by the implementer: Both a planning phase and invariants, decided by the user. THE PLANNING PHASE: decompose emits a short brief per MSP, enough for a planner and not enough to implement from. A planner then reads the WHOLE frozen SPEC plus that one MSP and produces the implementation plan. This strikes the thick-task decision entirely - it solved a problem that only existed because there was no planning layer. Deliberate asymmetry: the planner reads the SPEC, the implementer never does, so the planner has full context and the implementer's blast radius is bounded by what it was told. INVARIANTS: an invariant is a statement that must be true when the MSP is correctly built. It is NOT a test and NOT a description of the work. The planner determines the invariants and writes the statements only - it writes no test code. The implementer produces an executable assertion for each and proves each passes. ORDERING: CI must be green BEFORE invariants are asserted, because assertions run against working code; if CI later goes red the invariants must all be re-asserted. The two are independent - green CI says the system still works, passing invariants say this MSP did its job, and an MSP needs both. THE STRICT REQUIREMENT, and it is strict not aspirational: if every invariant passes and the MSP still does not work, the invariants were designed wrong. An invariant that can pass without meaning the MSP is correct is worthless. Designing invariants where "all pass" genuinely equals "correct" is the planner's core responsibility.
- D3 Write-sets schedule but never gate; clusters are dependency plus overlap chains, parallel across and sequential within: Write-sets are HINTS for scheduling, and file overlap creates an ordering edge. Both decided by the user. THE ALGORITHM, which is pure computation with no model and must be deterministic: nodes are MSPs; draw an edge between two MSPs when EITHER one declares the other in its needs OR their write-sets share at least one file; each connected group becomes one cluster; inside a cluster order MSPs so dependencies come first. EXECUTION RULE: clusters run at the same time as each other, and MSPs inside a cluster run one after another. A single cluster is a valid outcome - mitosis runs it sequentially and reports parallelism as one, it never refuses. INTENT BEHIND THE OVERLAP EDGE: this is the entire job of the write-set and the reason it is not deleted. The reason is NOT file corruption - separate worktrees make corruption impossible. The reason is VISIBILITY: the second MSP needs to see the first one's work. Two MSPs blindly adding different routes to one file can both register the same path and merge cleanly with a bug. INTENT BEHIND HINTS NOT GATES: a write-set is a guess made before the code exists, exactly as a human tech lead's would be. Enforcing it would pay a full rebuild for a guess that harmed nothing, and git catches the collisions that actually matter at merge. The declared-versus-actual difference IS recorded in the terminal report, so drift is visible without being acted on. ACCEPTED COST: an MSP can quietly touch a file it never declared and nothing stops it.
- D4 One pull request per MSP, stacked within a cluster; mitosis ends at PR open and never merges: One pull request per MSP, stacked within a cluster. Decided by the user. WHERE EACH PR POINTS: the first MSP in a cluster targets the feature branch; every later MSP in that cluster targets the branch of the MSP immediately before it. A cluster IS a stack. Independent clusters produce independent stacks, all pointing at the feature branch. WHY STACK: MSPs inside a cluster build on each other. If both pointed at the feature branch, the second PR's diff would contain the first one's changes too, because those changes are not merged yet and therefore look new. Stacking keeps each review showing only that MSP's own work. WHERE MITOSIS ENDS - this is the single responsibility and it is absolute: an MSP is shipped when its PR is open, CI is green on it, and every invariant has been asserted and passes. mitosis then stops. It NEVER merges any pull request. It NEVER ships the feature branch - a separate, future shipping adapter owns that. PRs are opened through the project's centralized pr-create tool in its mandatory format, never ad-hoc. ACCEPTED COSTS: more reviews (six MSPs means six reviews, not one), and a long chain reviews serially because each PR's base does not exist until the one below it merges.
- D5 No human between intake and the terminal report; git is the state; failure pauses rather than recovers: Unattended between intake and the report; git is the state; failure pauses. All decided by the user. THE HUMAN CONTACT RULE: phase 1 identifies anything genuinely ambiguous enough to change what gets built and asks EVERY question at once, in one message. Then the run goes dark and stays dark. A run that asks nothing is the normal case. INTENT: after intake nobody is watching, so a worker discovering mid-flight that the SPEC was unclear has already burned parallel work. All uncertainty resolves before anything spawns. WHERE REVIEW WENT: it did not disappear, it moved to the pull request, where a human reads real code instead of a plan predicting it. GIT IS THE STATE: no run-state file. A re-run reads existing branches and open PRs, and the decompose pass is told what already shipped so it plans only the remainder. A separate progress file is a second record of something git already knows, and a second record can go stale. FAILURE: the failing MSP pauses with its branch and work intact; every MSP after it IN THE SAME CLUSTER also pauses; other clusters are unaffected and finish normally. No retry counter and no attempt limit - a red build is a bug and fixing bugs is what the worker does. A human resolves the blockage and re-runs mitosis on the same SPEC. THE BAR THIS SETS, stated by the user and load-bearing for the whole design: mitosis can never be perfect and is not built to be. It is built to FAIL VISIBLY AND RECOVERABLY. When something is wrong it must show up as a rejected PR, a red build, a merge conflict, or a line in the terminal report - never as silence. ACCEPTED COST: a bad decomposition burns a full parallel run before anyone sees it, which is time and money, not correctness, since nothing merges without review.

## Open risks

- R1 Nothing downstream checks whether an invariant was well designed. If the planner writes weak statements - 'the file exists' rather than 'the raw key never reaches the database' - an MSP can be declared finished while doing nothing useful. This is the single largest correctness risk in the design, and it rests entirely on the planner.
- R2 Nobody sees the decomposition before workers spawn, so a bad split burns a full parallel run before a human looks. This is time and money, not broken code, because nothing merges without review - but it is the expensive failure and it is unattended.
- R3 Building in parallel does not mean reviewing in parallel. A four-deep cluster still needs four reviews in order, because each PR's base does not exist until the one below it merges. Long chains are the case where stacking hurts.
- R4 The superseded block-architecture report still exists at ~/.agent/diagrams/archive/mitosis-engine.SUPERSEDED-2026-09-07.html. It is 3.8MB, internally detailed, and VOID. A future session that reads it will restore decisions this design deleted. Do not open it.
- R5 RESIDUAL of the retired missed-MSP risk, which D1 coverage and the printed Coverage mapping largely close. What D1 cannot see: work the SPEC implies without naming - a migration, a config change, a docs update - and disagreement about how finely to cut. Neither appears as an unmapped line, because the SPEC never named them. Granularity is also unconstrained: the same SPEC could return four MSPs or forty, and that one choice sets parallelism, review load and stack depth.
- R6 Generalizing invariants to every phase makes invariant QUALITY the point the whole design rests on, in more places rather than fewer. Nothing checks whether an invariant was well designed - not MSP invariants, where 5.5 states the requirement with nothing enforcing it, and not the fixed phase invariants. A model affirming a statement it should have refused fails exactly like a weak statement, and leaves the same absence of signal.

## Settled, do not reopen

- S1 Out of scope: mitosis NEVER merges any pull request. It opens the PR and stops. A human merges.
- S2 Out of scope: mitosis NEVER ships the feature branch. A separate, future shipping adapter owns that.
- S3 Out of scope: No required SPEC format. No embedded block, no schema, no mandatory section, no validate CLI, no canonical example SPEC. There is nothing to teach an author.
- S4 Out of scope: No saved run-state file. Git is the state - a re-run reads existing branches and open PRs.
- S5 Out of scope: No human review between intake and the terminal report. Review happens at the pull request, on real code.
- S6 Out of scope: No completeness critic. It was a second model asking the decomposer's own question, producing findings nobody could act on.
- S7 Out of scope: mitosis does not review its own output. The pull request is the review surface.
- S8 Out of scope: No retry counter or attempt limit on a failing MSP. A red build is ordinary bug-fixing work.
