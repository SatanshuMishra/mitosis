- D5 The Reviewer phase dies entirely, replaced by the inertness gate: THE REVIEWER DIES ENTIRELY. Confirmed by the human. - D10 Round A: the failure model, resume, and the collapse of two gates into one: FANOUT'S FAILURE MODEL, VERIFIED: a Lane is ok/failed/blocked/resumed by EXIT CODE alone (fanout.py:1522); `doomed` marks downstream as blocked; a deadlock sweep marks unreachable Lanes "dependencies can no longer be satisfied"; finish_msp runs only when every Lane of the MSP is ok; exit non-zero on failed, blocked, or reconcile collisions ONLY. THREE NEW DEFECTS, all cross-referenced. GAP 8: the worker's reported `status` field is NEVER READ - only proc.returncode decides - so a worker printing {"status":"failed"} and exiting 0 is recorded ok and its MSP opens a PR; the return contract asks for a field nothing consumes. GAP 9: NO TIMEOUT ANYWHERE - no timeout, kill, terminate or deadline in 1878 lines, so a hung worker hangs the run indefinitely (failure class 5). GAP 10: five statuses never reach the exit code - merge-failed, push_error, pr-failed, finish-failed, no-branches - so there are five ways to make fanout's own claim ("a green exit is a claim") falsely. GAP 11: fanout's SPEC says `acceptance` "travels into the PR body so a cold session still has a test to re-run", but the PR template receives only {branch} {base} {title} {items} (fanout.py:1263-1266); acceptance reaches the worker's brief and stops. THE RECOMMENDED FAILURE MODEL: TWO LEVELS OF STATE because gates live at MSP level. Lane states ok / failed / blocked / merge-blocked, where ok requires exit 0 AND reported status ok (closing gap 8, since disagreement between the two channels is itself a failure) and merge-blocked is separate because the human action differs. MSP states shipped / gate-failed / gate-inconclusive / ship-failed. GATE FAILURES BLOCK THE CLUSTER BELOW THEM, because once stacking is on a Cluster is the shippable unit and a stack with a hole gives a dependent PR whose diff contains its predecessor's changes with no predecessor PR to merge - failure class 4; the alternative is technically possible since a stacked PR targets a branch not a PR, and is rejected for that reason. BLOCKING IS AFFORDABLE BECAUSE RECOVERY IS CHEAP: the Lanes are already ok and the work is committed, so resume re-runs only the gate. ORDER: all Lanes ok -> commit to the MSP branch -> gate -> push -> PR, committing BEFORE the gate because the probe needs a commit to branch from; a gate failure leaves a local commit on an unpushed branch. THE PROBE BRANCH IS DELETED IN A `finally` - the one piece of cleanup mitosis cannot skip. EXIT ZERO ONLY WHEN EVERY MSP REACHED shipped AND RECONCILE FOUND NOTHING, which is fanout's own stated principle applied to the five statuses it lets through. A PER-LANE TIMEOUT, caller-supplied with no default, killing the process tree and recording failed with reason timeout. RESUME AT TWO GRANULARITIES: Lane ok skips as fanout does, and an MSP with all Lanes ok but gate-failed SKIPS THE LANES AND RE-RUNS ONLY THE GATE - the main reason resume is worth specifying rather than inheriting. Keep fanout's plan_id guard (a resume against a different plan is a hard error). NEW STACKING HAZARD: a predecessor's PR merged and its branch deleted between runs - handle mechanically by checking whether its commits are reachable from the base, satisfied if yes and merge-blocked if no. Document drift reports but does not block resume. No cleanup on failure otherwise; worktrees and branches survive and the work is inspectable.
