# A built run relocks a locked check a fix repaired

Status: accepted. Amends 0006 and the per-MSP lock of 0016.

A locked check is held for the whole run. A committed change to a path the charter locks or to a check the lock stage wrote is restored at the gate and at ship, and its MSP is held back as `referee-reverted` with exit 9. That is right for a Worker and wrong for a defect inside the check itself. Acceptance run A3 of the pipeline, on the pull-request repository on 2026-11-15 with mitosis 0.22.0, is the case on record: a review round confirmed a defect in `tests/test_lint_split.py`, one of the run's two check files, its diagnosis named a complete fix, and two fix sessions made no commit because every instance was in a file no session may write. The MSP ended blocked with a draft pull request. That run's check-author was folded, so the rule that stopped the fix was the caller's and mitosis itself would have shipped a changed check with no proof at all; under a charter lock or a lock stage mitosis would have restored it. Neither shape had a way to keep a repair that review asked for.

A built run now has one. `--relock <MSP label>`, with one `--repairable <path>` for each locked check that may have changed, is added to the run's own invocation. It reads the plan and the state the run dir holds, plans nothing, dispatches no Worker, pushes nothing and moves no branch. Beside `--resume`, `--proven-head`, `--plan-only`, `--dry-run`, `--revise` or `--no-run-dir` it is a usage error.

The locked checks of an MSP are the paths its referee holds, which are the charter's locked paths and the checks its lock stage wrote, and, for a plan made from folded items, the files of the folded check-author Steps. The content a check is proved at is what its lock holds: the feature base for a charter path, the lock commit for a lock-stage check, and for a folded check the commit the MSP's Lanes landed, since the Step's own Worker wrote it there. To that is added what each earlier relock of the MSP proved, for as long as the branch still descends from that relock's commit. A check whose content at the branch head is none of those has changed. The anchor of a folded check is the Lanes' commit and not the gate's, because a gate that runs again after a caller's commit moves to the new head and would take an unproved change with it. The files of a folded check-author Step are read from `--items`, which must name the check-author Steps the plan folded and fold into the Steps the plan holds; an items file that does neither is not the one the run was built from, and the relock exits 2 rather than read a thinner list as nothing changed.

A changed check that was not named is a refusal, and so is one the fix removed. A changed check that holds an acceptance test of another MSP's Steps is refused too, because a relock runs only the tests of the MSP it was asked about: such a check is repaired and relocked on the MSP whose Steps hold its tests. So is any change when no acceptance test of the MSP that the gate runs lives in a locked check, since nothing would then be run against it.

Otherwise mitosis proves again what a lock proves. In a gate folder holding the MSP's base and the locked checks as the head holds them, every acceptance entry of the MSP's Steps that lives in a locked check must fail. An entry that does not fail there is run once more with the content proved before. When the repaired entry passes, it is a guard under 0024 only if the earlier content passed there too; where the earlier content failed or could not run, the repair has made the check unable to tell the work from its absence and the relock is refused. When the repaired entry cannot run, it is refused where the earlier content ran and failed, and accepted where the earlier content could not run either, which is every check that imports the work under a runner that collects before it runs. Every entry in the MSP's locked checks is run, not only those of the changed file, because one check file may import another. Then the MSP's gate runs at the head with the head's own checks, and every acceptance test must pass or be `not-applicable`.

A relock that holds writes the lock record of the MSP's locked checks at the head into the state, as the MSP's referee, in the k2 format unchanged, and adds the head to the relock journal, `relock/msp-<n>.json` in the run dir. The state and lock schemas stay as they are, because callers vendor them byte for byte. From then on the gate and the ship hold a relocked charter or lock-stage check at the latest proved content the branch holds: a later write is restored to the repair, and a repair put back to earlier proved content stands. A folded check is held by mitosis neither before nor after, so for that shape a relock is the proof and the record, and the caller's own rule keeps the hold. An MSP that merges another holds what that MSP's relocks proved as well as its own, so a stacked MSP ships the check its producer relocked and does not count it as changed; each journal lists only its own MSP's relocks.

A relock prints one JSON line, the paths it relocked and the reason it refused, and exits 0 when it held or found nothing changed, 1 when it refused and 2 when its flags or the run dir cannot be used. A refusal writes neither the state nor the journal, and the logs of its proof stay under `relock/msp-<n>`. A proof that could not be run, such as a `--gate-setup` command that failed, exits 2 and never 1, and so does an error mitosis did not expect, since 1 is the verdict a caller acts on by taking the fix back. A relock takes the hold a running mitosis keeps on the MSP's branch, so it cannot run beside a build or a ship of that branch, and it reads the state again at the moment it writes.

Three other shapes were weighed. Shipping the head through `--proven-head` alone drops the half of the proof that matters here: the caller proved the work, and nothing shows the check still fails without it, so a check loosened until it always passes would ship. Running the check-author again dispatches a Worker and replaces the repair review asked for with a check nobody reviewed. Writing a new lock commit under the branch moves the branch beneath commits review has already judged.

The proof has limits. It cannot tell a check loosened but still failing on the base from a repair, so the caller's review still judges what the fix did to the check. The run dir is trusted as the state is: whatever can write the journal can forge a relock, which 0030 leaves alone. The items file is trusted as far as a resume trusts it. A locked file that no acceptance test lives in is proved by the tests of the MSP it changed on and by no other MSP's. A folded check never had a check-author's probe, so failing on the base is all the first half shows.

The tests reach every rule above through the real entry point on a scratch repository, for folded, charter-locked and lock-stage checks, and each rule was removed once to see its test fail. The replay ran on copies of A3's run dir, run home and repository with the diagnosis's fix committed in the copy. The relock held in a little over two minutes, 11 acceptance entries failing on the base and 11 passing at the head, and the ship of that head to a stand-in remote holds the repaired file. An unnamed change was refused with the state byte for byte as it was. The same ship without a relock pushed the changed file too, which is the folded shape's missing hold and not a relock's doing.

This reopens when a relock refuses a repair that review accepted, when the cost of the proof per fix round matters, each entry in the MSP's locked checks running once on the base and once at the head, or when a caller needs mitosis itself to hold a folded check after its relock.
