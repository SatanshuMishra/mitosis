# Decisions for RFC 4648

Questions the document left open, settled. These are binding.

- The encoder never emits a line feed and exposes no wrap option. Line
  wrapping belongs to the referring specification's caller, not to this
  package.

- Omitting padding is a keyword-only `pad` flag defaulting to True on the
  encoder. Padding is emitted unless the caller asks otherwise.

- The strict decoder accepts non-zero pad bits by default and rejects them
  only when `reject_nonzero_pad_bits` is set. Section 3.5 states a MAY, so
  the permissive reading is the default and strictness is opt-in.

- Decoder input is `str` only. Bytes are not accepted, because the document
  defines the encoded form as characters of a US-ASCII subset.

- `map_confusables` reads 1 as I and 0 as O, and only for a scheme whose
  alphabet lacks that digit and contains that letter. It is therefore a no-op
  for base64, base64url, base32hex and base16.

- Trimming excess padding and restoring omitted padding are two separate
  functions, `trim_excess_pad` and `restore_padding`, so a caller may take
  one without the other.

- The three section 3.3 MAYs (ignoring non-alphabet characters, ignoring a
  pad before the end, ignoring excess trailing pad) are bundled under one
  `ignore_non_alphabet` flag. The section 3.2 omitted-pad case stays separate
  as `require_padding=False`.
