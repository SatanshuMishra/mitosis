# Decisions for Semantic Versioning 2.0.0

Questions the document left open, settled. These are binding.

- Two Version objects differing only in build metadata are NOT equal and do
  NOT hash alike. Equality is structural over every field. Shared precedence
  is expressed by `compare` returning 0, and that is the only place build
  metadata is ignored. The document says versions differing only in build
  metadata have the same precedence; it does not say they are the same
  version, and `str()` already keeps them distinct.

- Every increment drops pre-release identifiers and build metadata. The
  result of a bump is always a normal version.

- An increment applied to a pre-release bumps the number arithmetically, so
  `next_patch` of `1.0.0-alpha` is `1.0.1`. Reaching the associated normal
  version `1.0.0` is the separate operation `normal_version`.

- Under major version zero only a candidate of equal precedence is
  compatible. The caret convention that treats `0.y` as the compatibility
  line is not in the document and is not implemented.

- A pre-release candidate is never compatible, following the statement that a
  pre-release might not satisfy the compatibility requirements denoted by its
  normal version.

- `is_stable` is true exactly when the major version is at least 1 and there
  are no pre-release identifiers. Build metadata never affects stability.
